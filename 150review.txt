5.今までのプロジェクトで一番難しかった問題は何ですか。それはどのように解決しましたか。

SDK の API レスポンスをそのまま DTO に変換した結果、テスト時に大量の型エラーや構造不整合が発生しました。

現在の案件における課題点は、フロントエンドからBFFのAPIを呼び出し、その後さらにSDKのAPIを経由して他システムと連携し、レスポンス結果を処理した上でDTOに変換し、BFFのAPIレスポンスとしてフロントエンドに返却する必要がある点です。
複雑なデータ構造のマッピングや、TypeScriptによる厳格な型チェック、さらに100%のテストカバレッジを実現することが難しいポイントとなっています。

カバレッジテストにおいては、正常系だけでなく、条件分岐やエラー処理などの部分も100％テストカバレッジを達成する必要があり、テストケースの作成に多くの時間がかかる点が課題となっています。

NestJs进行dto变换的注意点
NestJSでデータ変換を行う際、SDK APIのレスポンスデータをDTO変換する前にはいくつか注意点があります。
特に、レスポンスデータの中にJSON形式の文字列が含まれている場合、そのままDTOに変換しようとすると型エラーや意図しないデータ構造になる可能性があります。
そのため、まずJSON文字列に対応した型定義のDTOファイルを作成し、正しい型に整えてから、外側のオブジェクトと統合してDTO変換を行う必要があります。
この手順を踏むことで、型安全かつ意図したデータ構造でサービス層やコントローラーに渡すことができ、後続の処理もスムーズに進められます。


6.ソースを書く時/コーディングする時、注意すべきこと/心掛けているのは何ですか。　
1. インターフェース規約の統一
リクエスト方式（GET/POST/PUT/DELETEなど）、パス、パラメータ形式、レスポンス構造を明確に定義する。
RESTfulやGraphQLなどの規約を推奨し、インターフェース名や内容を分かりやすくする。
2. データ型とバリデーション
前後でデータ型（string、number、boolean、配列、オブジェクトなど）を事前に取り決め、型不一致によるエラーを防ぐ。
バックエンドは入力値の厳格なバリデーションを行い、フロントエンドも基本的なチェックを実施する。
3. エラー処理の仕組み
バックエンドは統一されたエラーコードとメッセージを返し、フロントエンドはそれに応じて適切な処理（ダイアログ表示、リダイレクト、再試行など）を行う。
標準的なエラーレスポンス形式（例：{ code: number, message: string }）を取り決める。
4. セキュリティ
パラメータチェック、SQLインジェクション、XSS、CSRFなどのセキュリティ対策を徹底する。
機密性の高いインターフェースは認証（JWT、セッション、OAuthなど）を必ず実装する。
5. インターフェースドキュメント
Swagger、OpenAPI、Postmanなどのツールでインターフェースドキュメントを管理し、開発・テスト・連携を円滑にする。
ドキュメントは常に最新状態に保つ。
6. パフォーマンスと拡張性
ページング、フィルタ、ソートなどを考慮し、一度に大量データを返さない設計にする。
バッチ処理や非同期処理も検討し、パフォーマンスとユーザー体験を向上させる。
7. バージョン管理
インターフェース変更時はバージョン管理（例：/api/v1/xxx）を行い、既存クライアントへの影響を最小限にする。
8. クロスオリジンとCORS
バックエンドでCORS設定を正しく行い、フロントエンドから安全にアクセスできるようにする。
まとめ：
インターフェース規約、データ型、エラー処理、セキュリティ、ドキュメント、パフォーマンス、バージョン管理、CORS設定が前後端インターフェース設計の主な注意点です。

24.詳細設計書は何をもとに作成されていますか。
「詳細設計書は、主に『基本設計書』をもとに作成されます。」
基本設計で定義された画面レイアウト、データモデル、大まかな機能要件を受け取り、
それを「プログラムのクラス構成、関数仕様、エラーハンドリング、具体的なSQL文」といった実装レベルの仕様に落とし込むのが詳細設計の役割だからです。

また、基本設計書だけでなく、以下の要素も重要なインプット（もと）になります。
コーディング規約・アーキテクチャ設計書：プロジェクトで統一すべきコードの書き方やフレームワークのルール。
データベースの物理設計：実際にテーブルを作成するためのインデックス設計や型定義のルール。
共通部品（共通関数）仕様書：ログ出力や認証チェックなど、システム全体で使い回す共通処理の仕様。

30.業務フロー/ユーザーケース設計をした経験はありますか。

担当した主要なフロー：

「注文確定から出荷完了までの裏方業務フロー」
ユーザーが決済を完了（API Gateway/Lambda） ➔ SQSキューに注文データが自動格納 ➔ 物流システム（WMS）へCSVで出荷指示 ➔ 倉庫でピッキング・発送 ➔ 配送追跡番号をECシステムへ書き戻し ➔ 顧客へLINEで発送完了通知。

担当した主要なユースケース：

アクターの定義：一般顧客、定期購入ユーザー、EC店舗管理者、物流システム（システムアクター） の4つを定義。
ユースケース記述（仕様書の作成）：
例えば【ユースケース名：商品画像を登録して最適化する】というユースケースに対し、以下のような「ユースケース記述書」を作成しました。
基本アクター：EC店舗管理者
前提条件：管理画面にログインしていること
メインシナリオ：管理者が出品画面でJPG画像をアップロードする ➔ システムがS3に保存する ➔ Lambdaが起動しWebPに変換する ➔ 完了メッセージを画面に表示する。
例外シナリオ：アップロードされたファイルが画像形式（JPG/PNG）以外だった場合、エラーを表示して処理を中断する。

2. 要件定義（ユーザーの要望）とのトレーサビリティ（追跡可能性）があるか
チェック例：

要件定義書に書かれていた「セール時にサイトを落とさない」という要件に対し、この基本設計（インフラ・API Gatewayの制限値など）で本当に担保できているか。


3. 画面・API・データベース間の「データの整合性」
チェック例：

画面設計書にある「肌悩みタグ」という入力項目が、データベース設計（ER図・テーブル定義）やAPIのI/F（インターフェース）仕様書に正しくマッピングされているか。

「表示するデータ」と「保持するデータ」の型や桁数がズレていないか。

4. 後続のプログラマーやデザイナーが「迷わない記述」になっているか
チェック例：

仕様が曖昧なまま「〜等」「状況に応じて処理する」といった抽象的な表現で濁されていないか。

この設計書を渡されて、プログラマーが「どう実装すればいいか」のイメージを明確に持てるか。


5. セキュリティとパフォーマンス（非機能要件）
チェック例：

APIの設計において、二重サブミット（連打による多重決済）の防止策が設計されているか。

大量データが想定される機能において、データベースの「N+1問題」や「テーブルフルスキャン」を引き起こすような設計になっていないか。




40.設計書はレビューされた時、どんな指摘一番多かったでしょうか。

具体的にどのような指摘が多かったのか、実例とともに3つのカテゴリーに分けてご紹介します。

 1. 【最多】例外系・異常系の考慮漏れ
ハッピーパス（ユーザーが想定通りに操作し、システムが正常に動くルート）は綺麗に書けているものの、「もしここでエラーが起きたらどうするの？」という指摘が最も多かったです。

64.Java EEの3層構造とは何ですか。
各層（レイヤー）の具体的な役割
① プレゼンテーション層（画面・制御）
役割：ユーザー（ブラウザ）との窓口です。画面を表示したり、ユーザーが入力したデータを受け取って「ビジネスロジック層」へ引き渡します。

Java EEでの主な技術：JSF (Jakarta Server Faces)、JSP、Servlet、JAX-RS（RESTful APIのコントローラー）


② ビジネスロジック層（業務処理）
役割：システムの「頭脳」となる部分です。ビジネス上のルールや計算、処理手順（ロジック）をここに集約します。この層は画面のデザインや、データベースの種類（MySQLやOracleなど）を一切気にしません。

Java EEでの主な技術：EJB (Enterprise JavaBeans)、CDI (Contexts and Dependency Injection)


③ データアクセス層（永続化・DB操作）
役割：データベースなどの外部システムとデータをやり取りする専門の層です。ビジネスロジック層からの指示を受けて、データの登録（Insert）や検索（Select）を行います。

Java EEでの主な技術：JPA (Jakarta Persistence / 旧Java Persistence API)、JDBC

109.負荷テストをやったことがありますか。
はい、JMeter ジェイメーターを使用した負荷テスト（性能・ストレステスト）の実務経験があります。

Step 1: 目的と目標値の決定（計画）

HTTP Request: テスト対象の URL や API エンドポイント（GET/POST）を設定。

HTTP Header Manager: 認証トークン（Authorization: Bearer ...）や Content-Type: application/json を付与。

CSV Data Set Config: ログイン ID や動的パラメータを CSV から読み込み、並列処理でのデータ重複を回避。

Assertion（検証）: レスポンスコード 200 や特定文字列の有無チェックを設定。

Step 3: データ準備とスクリプト検証（ドライラン）
DB にテスト用ユーザーやマスターデータを事前投入。

少人数（1 ユーザー / 1 ループ）でテストを実行し、エラーなくリクエストが飛ぶか確認。

生成された HTML レポートやサーバーログを分析します。

123.テスト結果のエビデンスのレビューはされていたか。その時やり直しはあったか。どんな指摘をよく受けたか。
1. 事前状態（Before）の取得漏れ
指摘内容: 「処理実行後（After）のDBキャプチャや画面はあるが、実行前（Before）の状態が残っていないため、今回のテスト操作によって正しくデータが変化したのか（元からそのデータだったのではないか）が証明できない」

やり直しの理由: データの状態変化（UPDATEやDELETE）を伴うテストにおいて、比較対象がないため。

改善策: テスト開始直後に必ずDBの SELECT 結果や一覧画面の初期状態をスクショ・保存する癖をつけました。


2. 異常系テストにおける「裏側の確認」漏れ
指摘内容: 「画面上に『システムエラー』のメッセージが出ているエビデンスはあるが、裏側のDBに不正なデータが登録されていないこと（ロールバックされたこと）のエビデンスがない」

やり直しの理由: 表面上はエラーに見えても、裏側でデータ不整合が起きている（サイレント障害）可能性を払拭できないため。

改善策: 異常系のテスト（エラーハンドリング）を成功とするには、「画面のエラー表示」＋「DBやサーバーログの無事（変更なし）」をセットで証明するよう意識を変えました。

125. AWSでプロジェクトをリリースするときどんな技術を使用しましたか。
ローカル環境から GitHub へ git push を実行すると、GitHub 側で検知された Webhook イベントが AWS CodeConnections の接続を伝達され、これに連動して CodePipeline が自動的にパイプラインを起動します。

Source および Build ステージ：CodePipeline が最新のソースコードを自動的にダウンロードし、CodeBuild を起動します。CodeBuild は特権モード（Privileged）環境で docker build を実行し、
ビルドされた最新のイメージを Amazon ECR にプッシュすると同時に、デプロイスクリプトを含むアーティファクト（展開マニフェスト）を出力します。

Deploy ステージ：CodePipeline がデプロイ情報を CodeDeploy サービスに引き渡します。

EC2 インスタンスでの実行：EC2 上で稼働する CodeDeploy Agent がクラウドからのデプロイ指示を検知し、deploy.sh スクリプトを自動的にダウンロードしてローカル環境で安全に実行します。
このスクリプトは AWS 認証を通じて ECR にログインし、旧コンテナの停止、ECR からの最新イメージのプル、およびアプリケーションのシームレスな再起動を行います。


126.EC2 / RDS / S3 / EKS/ ECRはそれぞれどんなサービスでしょうか。
EC2（イーシーツー）「AWSの中に作れる、自分専用のレンタルパソコン（サーバー）だよ」。
RDS（アールディーエス）「面倒な設定や管理を全部AWSがやってくれる、データ保存用の箱（データベース）だよ」
S3（エススリー）  「容量無限で、めちゃくちゃ安くて壊れない、クラウド上の特大ファイル置き場だよ」
EKS（イーケーエス）「たくさんのDockerコンテナを、自動でいい感じに管理・運用してくれるサービスだよ」もっと詳しく： コンテナを管理する「Kubernetes（クバネティス）」という難しい仕組みを、AWS上で簡単に使えるようにしたサービス。大規模なシステムでコンテナが何十個、何百個になっても自動でスケールさせてくれます。
ECR（イーシーアール）「自分たちのプロジェクトで作ったDockerイメージを、安全に保管しておく専用の倉庫だよ」もっと詳しく： さっきのCodePipelineの会話でも出てきた、Dockerイメージのプライベートな置き場です。ここにイメージを預けておいて、EC2やEKSがそれを引き抜いて（Pullして）アプリを起動します。

 1. 安全で堅牢なネットワークインフラ設計（VPC/セキュリティ）
安全なネットワーク分割：パブリックサブネットとプライベートサブネットを明確に分け、データベース（RDS）やコンテナ基盤（EKS/ECS）などの基幹系をプライベートスペースに完全隔離する設計。

自動スケール：CPU負荷やリクエスト数に応じてサーバー数を自動で増減させる Auto Scaling の設計・導入。

 3. 近年のモダンなクラウドネイティブアーキテクチャ（コンテナ・サーバーレス）
コンテナ運用基盤：Amazon ECS (Fargate) や Amazon EKS を用いた、OS管理フリーで拡張性の高いコンテナオーケストレーション環境の設計・構築。

サーバーレス：AWS Lambda、Amazon API Gateway、Amazon DynamoDB を組み合わせた、サーバーの常時起動コストをゼロにするイベント駆動型システムの構築。

4. インフラのコード化（IaC）と自動化
Terraform / AWS CloudFormation：コンテナ、VPC、IAMなどのインフラ一式をコード化し、ボタン一つで同じ環境を「ステージング用」「本番用」とクローンできる環境の構築。

CI/CD連携：今回のテーマにもあった AWS CodePipeline / CodeBuild / CodeDeploy や GitHub Actions を用い、GitHub への git push から ECR へのイメージ登録、ECS/EC2 へのゼロダウンタイム（藍緑）デプロイまでの完全自動化。

133.データ移行する際、何か障害が発生したことがありますか。

本番データの「イレギュラー（外れ値）」による移行バッチ停止
旧システムから新システムへ顧客データをバッチ処理で移送・変換（ETL）していた際、想定外のデータが含まれており、移行バッチが途中でクラッシュ（異常終了）しました。

原因:
旧システムのデータベース上、通常は入力されるはずのない NULL や制御文字、超ロング文字列（仕様外の文字数）が過去の運用データ内に残存していたため、新システムのバリデーションチェックに引っかかりました。

影響:
テスト環境のダミーデータ（きれいに整理されたデータ）では正常終了していたため、本番移行の当日になって初めて発覚し、移行作業時間が大幅に延びました。

対策（教訓）:

本番移行の前に、本番データを個人情報マスキングした上で「事前リハーサル（ドライラン）」を必ず実施し、データの全件洗い出しとクレンジング（事前補正）を行う運用に変えました。

移行スクリプト側も「1件エラーが起きても全体を止めず、エラーログを出力してスキップ（またはデッドレターキューへ退避）し、後から個別リトライできる構造」に修正しました。


文字コード変換・文字化けによるデータ破損
旧システムの文字コード（Shift-JIS / Windows-31J）から新システム（UTF-8）へデータをコンバートする際、外字や特殊文字（旧字体・環境依存文字）が文字化け（? や  に置換）しました。

移行前に旧DB内で「環境依存文字・非ASCII文字」が含まれるレコードを抽出する SQL スクリプトを作成し、事前に変換ルールを定義・テストするようにしました。




134.データ移行する際、データを読んでいる先を変えないといけないと思います。その辺対応したことありますか。


一括切り替え（Big Bang Approach / メンテ時間を設ける場合）
夜間や休日にシステムを一時停止（メンテナンス状態）にし、データの最終同期を行った上で一気に参照先を切り替える最も標準的な手法です。

切り替え方法:

DNS / ロードバランサー（ALB等）の切り替え: ユーザーからのドメインアクセス先（例: api.example.com）の向き先を、旧環境のIPから新環境のIPに変更。

環境変数 / 設定ファイルの書き換え: アプリケーション側の DB 接続文字列（JDBC URL やホスト名）を書き換えて再起動。


段階的切り替え / 2重書き込み（Dual Write / メンテ時間を最小化・無停止にする場合）
無停止（Zero Downtime）または短時間の停止で移行したい場合に用いる高度な手法です。

 [ ユーザー ]
     │
     ▼
 [ 新API / Gateway ] ───(1. 参照は新DBへ)───► [ 新 DB ]
     │
     └───(2. 更新は両方へ同期/2重書き)───► [ 旧 DB ] (切り戻し担保用)
切り替え方法:

旧DB ➔ 新DB へのリアルタイムレプリケーション（CDC: Change Data Capture）: AWS DMS（Database Migration Service）や Debezium 等を使い、旧DBの変更差分をリアルタイムで新DBへ流し込む。

アプリケーション側でのスイッチ制御: フィーチャーフラグ（Feature Flag / 設定値）を用いて、「特定のユーザー群だけ参照先を新DBに変える」といったカナリアリリース（段階切り替え）を実施。

142.ETLという技術はご存知でしょうか。

はい、ETL（Extract / Transform / Load）はよく知っており、データ移行やデータ分析基盤（データウェハウス：DWH）の構築などで深く関わるコア技術です。

システム間のデータ連携や、旧システムから新システムへデータを移送・加工して格納するプロセスにおいて中心的な役割を果たします。


[データソース]               [ETLプロセス]               [ターゲット]
 (旧DB / CSV / API) ──►  E ──► T ──► L  ──► (新DB / DWH / BI)


Extract（抽出）:

様々なデータソース（RDB、NoSQL、CSV/TSVファイル、外部Web API、ログファイルなど）から、必要なデータを取得する処理。

Transform（加工・変換）:

抽出したデータを、移行先・保存先のフォーマットに合わせて変換する処理。

主な処理: データ型の変換、文字コード変更（Shift-JIS ➔ UTF-8）、不要データのクレンジング（NULL補正や不要行の除外）、テーブル結合・集計、名寄せなど。

Load（書き込み・格納）:

加工後のデータを、ターゲット（新システムのDB、データウェアハウス（Snowflake / BigQuery 等）、データレイク）へ書き込む処理。




本番データ特有の「外れ値」対策（Transform段階）:

旧DBに存在する想定外の型・文字数・NULLデータなどにより、TransformやLoadの段階で処理がクラッシュしないよう、不整合データの検知（バリデーション）とエラーログ化（スキップ処理）を設計します。

大量データ挿入の高速化（Load段階）:

数百万件規模のLoadを行う場合、1件ずつ INSERT すると膨大な時間がかかります。そのため、バルクインサート（Bulk Insert / Copy コマンド）の利用や、一時的なインデックス・制約の無効化（Disable/Drop）を行ってパフォーマンスを最大化します。

ETLツールの活用:

Python（Pandas）や SQL（Stored Procedure）等でスクリプトを自作するケースもあれば、AWS Glue, Talend, Apache NiFi, Informatica などの専用ETL/ELTツールを活用してパイプラインを自動構築・監視するケースもあります。

要件定義は、発注者（顧客・業務部門）の「実現したいこと・課題」を吸い出し、システムとして「何を（What）構築するのか」を明確にして合意形成を図る非常に重要な工程です。

1. 業務要件（Business Requirements）に関する書類
業務の「現状（As-Is）」と「理想（To-Be）」を整理し、新システムでどのように業務が変わるかを提示するドキュメントです。

業務フロー図（As-Is / To-Be 業務フロー）:

業務の流れ、関係する部署・担当者、新システムとの境界を可視化したフロー図（BPMNやスイムレーン形式）。

業務要件定義書:

システム化の目的、解決すべき課題、期待される効果（KPI）、業務上のルールや制限事項をまとめた文書。

2. 機能要件（Functional Requirements）に関する書類
システムが具体的に「どのような機能を提供するか」を定義するドキュメントです。

機能一覧表（機能要件定義書）:

システムが持つべき全機能を洗い出し、大・中・小分類、優先度（Must / Should / Want）、概要を一覧化（WBSや進捗管理のベースにもなる重要書類）。

画面一覧・画面遷移図・ワイヤーフレーム（画面イメージ）:

画面のレイアウト（ラフ案）や画面間の遷移関係を示し、顧客と具体的なUI/UXのイメージを共有・合意するための資料。

ユースケース記述書 / ユーザーカンプ・ユーザーストーリー:

「誰が（アクター）」「どのような目的で」「どんな操作・処理を行うか」をシナリオ形式で整理した書類。

データモデル（概念データモデル / 概念ER図）:

新システムで扱う主要な情報（ユーザー、注文、商品、決済など）とその相互関係（リレーション）を整理した図。

外部システム連携要件定義書:

既存システムや外部サービス（決済API、会計システムなど）との連携方式（API、ファイル連携、バッチなど）、連携データ項目、頻度を定義した資料。


147.要件定義した際に顧客様と直接会話したことありますか。最終クライアントの方ですか、Sir企業の方ですか。
はい、要件定義工程において顧客様と直接お打ち合わせ・交渉を行った経験が豊富にございます。

お相手の立場についても、「最終クライアント（事業会社・エンドユーザー）様」および「元請け・SIer（Primary System Integrator）企業様」の両方のパターンでの直接対話・ファシリテーション経験がございます。

主に事業会社（EC、金融、製造、サービス業など）の業務部門（現場のユーザー）や情報システム部（情シス）の担当者様・責任者様と直接お話ししたケースです。
業務課題・ニーズの吸い出し:

専門用語を使わず、「現在どのような業務手順で困っているか」「新システムで業務をどう効率化したいか」をヒアリングし、業務フロー図（To-Be）として可視化して共有。

画面イメージ（UI/UX）やユースケースの提示と合意:

ワイヤーフレーム（画面の骨組み）やプロトタイプを用いて、「実際の業務でこの画面構成で操作しやすいか」を具体的に提示し、納得感を持ちながら合意形成。

スコープ・優先度の交渉:

予算や納期（リリース時期）の制約の中で、ご要望に優先度（Must / Want）を付け、「今回のリリースで対応する範囲」と「次期フェーズに回す範囲」を整理・提案。



元請けのPM（プロジェクトマネージャー）様やPL（プロジェクトリーダー）様、ITコンサルタント様と対話したケースです。

システムアーキテクチャ・非機能要件のすり合わせ:

性能目標（レスポンスタイム、スループット）、セキュリティ基準、可用性（障害復旧時間）などの技術要件を具体化。

他システム連携仕様（IF仕様）の調整:

元請け側が管理する基幹システムや他ベンダーが開発するシステムとの連携方式（API定義、ファイルフォーマット、データ保持期間など）のネゴシエーション。

仕様の漏れ・実現性の検証（実現可否の判定）:

エンドユーザーから降りてきた要件に対し、「技術的に実現可能か」「スケジュール・コスト内に収まるか」を技術的観点からフィードバックし、妥当な仕様への着地をサポート。

149.管理職とエンジニア作業範囲の違うを教えてください。
管理職（マネジメント職）とエンジニア（プレイヤー・技術職）は、プロジェクトや組織における「目的」「役割」「評価される成果」が大きく異なります。

一言で言うと、エンジニアは「技術でモノを作り上げる役割」であり、管理職は「人・予算・計画をくり繰りくりくり管理し、チームで成果を出させる役割」です。



150.チーム管理するの難関を述べてください、具体例も教えてください。
チーム管理（マネジメント）における難関は、一言で言うと「コントロールできない『人』や『不確実性』を扱いながら、チームとして約束した成果（納期・品質・予算）を出し続けなければならない点」にあります。
