目前案件的困难点
現在の案件における課題点は、フロントエンドからBFFのAPIを呼び出し、その後さらにSDKのAPIを経由して他システムと連携し、レスポンス結果を処理した上でDTOに変換し、BFFのAPIレスポンスとしてフロントエンドに返却する必要がある点です。

複雑なデータ構造のマッピングや、TypeScriptによる厳格な型チェック、さらに100%のテストカバレッジを実現することが難しいポイントとなっています。

カバレッジテストにおいては、正常系だけでなく、条件分岐やエラー処理などの部分も100％テストカバレッジを達成する必要があり、テストケースの作成に多くの時間がかかる点が課題となっています。

NestJs类型转换dto的注意点

NestJSでデータ変換を行う際、SDK APIのレスポンスデータをDTO変換する前にはいくつか注意点があります。

特に、レスポンスデータの中にJSON形式の文字列が含まれている場合、そのままDTOに変換しようとすると型エラーや意図しないデータ構造になる可能性があります。

そのため、まずJSON文字列に対応した型定義のDTOファイルを作成し、正しい型に整えてから、外側のオブジェクトと統合してDTO変換を行う必要があります。

この手順を踏むことで、型安全かつ意図したデータ構造でサービス層やコントローラーに渡すことができ、後続の処理もスムーズに進められます。

同様の事象が発生しないよう、対応手順をまとめました。チームチャットにも共有済みですので、参考になれば幸いです。

AWSを学び始めたきっかけは、友人が新しくオープンした焼肉店向けにQRコード注文サイトを提供する必要があったことです。アクセス量がそれほど多くないため、従来のサーバー購入よりも、AWSのクラウドサーバーをレンタルしてシステムを構築した方が運用・保守コストを大幅に削減さくげんできると考え、本格的にAWS上でのWebサービス構築を学び始めました。

焼肉店の注文システムを構築した経験を通じて、AWS上でのシステム構築がデプロイや運用面で非常に便利であることを実感しました。そのため、この分野でさらに自分のスキルを高めていきたいと考えています。

個人プロジェクトを制作した理由は、Reactのアニメーションコンポーネントライブラリの効果に非常に興味があり、実際のプロジェクトでその活用を試してみたいと考えたためです。

Webアプリケーションのフロントエンド・バックエンド開発には自信がありますが、クラウドサービスのアーキテクチャ設計についてはまだ経験が浅く、今後さらに実践力を高めていきたいと考えています。

はい、AWSの構築は自分で設計しました。要件に合わせてVPCやEC2、RDS、IAMなどの構成を考え、セキュリティや運用面も含めて全体のアーキテクチャを自分で設計・構築しました。

Docker Composeで作成したイメージをAWSのElastic Container Registry（ECR）にプッシュして一元管理し、その後AWS Elastic Container Service（ECS）を利用してデプロイ・運用しています。

Azureアジュールを学習しており、主要サービスとAWSの対応関係を把握しています。

たとえば、AzureのVirtual MachinesバーチャルマシンズとバーチャルネットワークはAWSのEC2とVPCに相当し、スムーズにマッピングできます。

絞り込みの選択性が高いカラムほど効果が大きい

単一たんいつカラム／複合ふくごインデックスの作成

単一カラム：検索条件が1列のみの場合

複合インデックス：複数列を同時に使う場合（WHERE a=? AND b=? のようなパターン）

カバリングインデックスの検討

SELECT句全列をインデックスに含めることで、テーブルアクセスを回避

例：SELECT col1,col2 FROM table WHERE col1=? → CREATE INDEX idx_cover ON table(col1,col2);

関数／計算列の注意

WHERE YEAR(created_at)=2025 のような関数適用はインデックスを無効化するため、

WHERE created_at BETWEEN '2025-01-01' AND '2025-12-31' のように書き換える

数据库设计范式

第一范式：每一列都是不可分割的原子数据项

   第二范式：在第一范式的基础上，非码属性必须完全依赖于候选码(在第一范式的基础上消除非主属性对主码的部分函数依赖）

   

   几个概念：

   1.函数依赖：A-->B，如果通过A属性的值，可以确定唯一B属性的值。则称B依赖于A

    例如：学号-->姓名。 （学号，课程名称）-->分数

   2.完全函数依赖：A-->B，如果A是一个属性组，则B属性值的确定需要依赖于A属性组中所有的属性值。

   例如：（学号，课程名称）-->分数

   3.部分函数依赖：A-->B，如果A是一个属性组，则B属性值的确定只需要依赖于A属性组中某一些值即可。

   例如：（学号，课程名称）-->姓名

   4.传递函数依赖：A-->B，B-->C，如果通过A属性（属性组）的值，可以确定唯一B属性的值，

   在通过B属性（属性组）的值可以确定唯一C属性的值，则称C传递函数依赖于A

   例如：学号-->系名，系名-->系主任

   5.码：如果在一张表中，一个属性或属性组，被其他所有属性所完全依赖，则称这个属性（属性值）为该表的码

   例如：该表中码为：（学号，课程名称）

   主属性：码属性组中的所有属性

   非主属性：除码属性组的属性

   第三范式：在第二范式的基础上，任何非主属性不依赖于其它非主属性（在第二范式的基础上消除传递依赖）

乐观锁

楽観的ロックの原理は、テーブルのレコードに保存されている「更新日時」を利用して管理する方法です。データの更新時に、現在の更新日時と取得時の更新日時を比較し、一致していれば更新を許可し、異なっていれば他のトランザクションによる変更があったと判断して更新を拒否します。これにより、同時更新の競合を防ぐことができます。

はい、CI/CDパイプラインの構築と運用経験があります。具体的には、GitHub Actionsを利用して、Reactプロジェクトの自動テスト・ビルド・デプロイを設定しました。プッシュやプルリクエストのタイミングでユニットテストを自動実行し、テストが通過した場合のみ本番環境へ自動デプロイするワークフローを構築しました。これにより、開発効率や品質の向上を実現できました。YAMLファイル（.github/workflows/*.yml）を作成し、

name: 依存関係のインストール

run: npm install

name: テストの実行

run: npm test

などの手順を定義することで、継続的インテグレーション（CI）や継続的デリバリー／デプロイ（CD）を実現できます。
