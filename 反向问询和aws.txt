aws RDS实例构造和访问的手顺
まず AWS コンソールにログインして、RDS → Databases → Create database を開いてください。
使いたいエンジン（MySQL／PostgreSQL／MariaDB／Oracle／SQL Server／Aurora）を選びます。
テンプレート（Production か Dev）、バージョン、インスタンスタイプ（例：db.t3.medium）、ストレージ種別と自動拡張を設定します。
可用性ゾーンと Multi‑AZ の設定を選択します（本番なら Multi‑AZ を有効にすることをおすすめします）。
認証方法（ユーザー名／パスワード または IAM 認証）を設定します。
VPC と DB Subnet Group を選び、「Publicly accessible」は通常オフ（非公開）を推奨、Security Group はアプリや踏み台からのアクセスを許可するルールにします。
バックアップ、メンテナンスウィンドウ、監視（Enhanced monitoring / Performance Insights）を設定します。
作成後、インスタンスが available になるまで待ち、Endpoint と Port をメモしておきます。

cloudwatch主要监控指标
- 指標（Metrics）：CPU、メモリ、IO、ネットワークなどの時系列データで、リソース使用や性能傾向を監視します。
- ログ（Logs / Logs Insights）：アプリ／システムログの収集・検索・分析を行います。
- アラーム（Alarms）：指標の閾値や異常を検知して通知や自動アクション（例：SNS通知、Auto Scaling）を起動します。
- ダッシュボード（Dashboards）：複数の指標やグラフを一画面で可視化し、運用や報告に利用します。
- イベント・トレース連携：CloudWatch Events/EventBridge、CloudWatch Synthetics、X‑Rayの分散トレースと連携して原因分析や監視を強化します。

プロジェクト背景

本プロジェクトは AWS 上に展開される人事管理システムであり、従業員の個人情報、給与、勤怠データなどを外部へ API で提供する一方、厳重な保護が求められます。

システムはフロントエンド、ミドル層（ビジネスサービス）、バックエンド（データベース）から構成され、ネットワーク分離、セキュリティ、可用性が重要な要件となっています。

VPC 設計要点

サブネットの分割

• パブリックサブネット：Application Load Balancer（ALB）を配置

• プライベートサブネット：EC2（API サービス）および RDS データベースを配置

またCloudWatch でサブネット／NAT／IGW のトラフィックを監視し、異常時には自動アラート通知を実装

Lambda和ecr的应用场景

イベント駆動、サーバーレス、自動化、APIバックエンドが必要な場合はLambda APIを利用。

コンテナ化、イメージ管理、複雑な依存やマイクロサービス構成が必要な場合はECRを利用します。

AWSAPI设计

AWS上でRESTful API＋Lambdaを使ってAPIサービスを構築する場合、主に以下のステップ・ポイントがあります。

AWS LambdaとRESTful APIサービスの一般的な設計アーキテクチャは以下の通りです。

【アーキテクチャ概要】

API Gateway

RESTful APIのエントリーポイントとして機能し、ルーティングや認証、リクエスト制御などを担当します。クライアントからのHTTPリクエスト（GET/POST/PUT/DELETEなど）を受け付けます。

Lambda関数

API Gatewayのルーティング設定に従い、対応するLambda関数がトリガーされます。Lambda関数内でビジネスロジックやデータ処理、外部サービスの呼び出しなどを実装します。Lambdaはサーバーレス（Serverless）アーキテクチャであり、リクエスト数に応じて自動的にスケールします。

データストア／外部サービス

Lambda関数はDynamoDBやRDS、S3などのAWSサービス、または外部APIにアクセスできます。処理が完了したら、その結果をAPI Gatewayに返します。

クライアントへのレスポンス

API GatewayがLambdaの返却値をHTTPレスポンスとしてクライアントに返します。

【主な特徴】

サーバーレス：サーバー管理が不要で、自動的にスケールします。

イベント駆動：各APIリクエストごとにLambdaが実行されます。

高可用・低運用コスト。

マイクロサービスやBFF（Backend For Frontend）構成にも適しています。

ご要望に応じて、さらに詳細な設計やコード例もご案内可能です。

Lambda和step function ステップファンクションズ
AWS Step Functions を利用して定時実行のワークフローを構築し、複数の Lambda 関数を順番に呼び出します。

EventBridge のルールは、イベントに応じて Lambda と Step Functions を同時にトリガーできます。Step Functions はオーケストレーターとして Lambda を呼び出してタスクを実行し、逆に Lambda から Step Functions の実行を開始・トリガーすることも可能です。両者は同期／非同期呼び出し、イベントバス、タスクトークン（コールバック）などで連携します。

Lambda＋RESTful APIと従来型のバックエンドAPIサーバー構築の具体的なコード実装上の違いは、主に以下の点に現れます。


まとめ：

Lambda＋RESTful APIは「関数単位」「イベント駆動くどう」「サーバーレス」な実装スタイル、

従来型は「常駐サーバー」「ルーティング中心」「プロセス管理あり」の実装スタイルが特徴です。

AWS Lambda APIを利用する際の注意点は以下の通りです。

権限管理

Lambda関数に必要なIAM権限を付与し、アクセスするAWSサービス（S3、DynamoDB、API Gatewayなど）に適切な権限があることを確認してください。

API GatewayからLambdaを呼び出す場合も、正しい権限設定が必要です。

タイムアウトとリソース制限

Lambdaには最大実行時間（デフォルト3秒、最大15分）があり、タイムアウトすると強制終了されます。

メモリやCPUリソースも制限されているため、用途に応じて適切に設定してください。

コールドスタート問題

初回呼び出しや長時間未使用時はコールドスタートによる遅延が発生することがあります。

API Gateway連携

API Gateway経由でLambdaを呼び出す場合、リクエスト・レスポンスの形式（event、context、JSON返却）に注意してください。

CORS（クロスオリジン）設定も正しく行う必要があります。

ログ・監視

CloudWatchを利用してログやパフォーマンスを監視し、問題発生時のトラブルシュートに役立ててください。

環境変数・設定管理

機密情報は環境変数やAWS Secrets Managerで管理し、コード内に直接記載しないようにしてください。

エラー処理

Lambda内の例外は適切にキャッチし、API Gatewayに正しいエラーレスポンスを返すようにしてください。

依存パッケージ管理

デプロイ時に必要な依存パッケージをすべて含めるか、Layerを利用して不足がないようにしてください。

まとめ：

権限、タイムアウト、コールドスタート、API Gateway連携、ログ監視、環境変数、エラー処理、依存パッケージ管理がLambda API利用時の主な注意点です。

人事管理システム機能との連携

ルートテーブルとゲートウェイ

• Internet Gateway：パブリックサブネットをインターネットに接続

• NAT Gateway：プライベートサブネット内インスタンスのパッチ適用・依存ライブラリ取得を許可

セキュリティグループ／ネットワーク ACL

• ALB セキュリティグループ：TCP 443／80 のみインターネットから許可

• API サービス SG：ALB および踏み台サーバーからのアクセスのみ許可

• データベース SG：プライベートサブネット内の API サービスからの 3306 ポートのみ開放

可用性と監視

複数 AZ にまたがるサブネット配置で、単一 AZ 障害時のサービス継続性を確保

従業員ログイン・個人情報クエリ API：パブリックサブネット上の ECS／Fargate または EC2＋ALB で提供

給与・勤怠など機密業務ロジック：プライベートサブネット上で実行。さらに踏み台サーバーの代わりに AWS Systems Manager Session Manager を用いたセキュア運用を採用可能

データベース：プライベートサブネット内の RDS を Multi-AZ／自動バックアップ設定で配置し、高信頼性・回復性を担保

成果と価値

ネットワークを多層化することで分離性とセキュリティが向上し、人事データの機密性・コンプライアンス要件を満たす

Terraform モジュールや CloudFormation テンプレートでインフラをコード化し、迅速かつ再利用可能な環境構築を実現

CloudWatch 監視＋自動アラートにより障害対応リードタイムを短縮し、人事システムの安定稼働を支援

AWSのアーキテクチャでは、CloudWatchからSNS（Simple Notification Service）を経由してメール通知やSlackへのリマインダーを実現できます。一般的な流れは以下の通りです。

CloudWatchでイベントやアラームを監視

　例：EC2、Lambda、API Gatewayなどの監視指標やカスタムアラーム

CloudWatchアラームがSNSトピックをトリガー

　CloudWatchアラーム設定でSNSトピックを通知先として指定

SNSトピックのサブスクリプション設定

　- メールサブスクリプションを追加（アラーム発生時に自動でメール送信）

　- HTTP/HTTPSサブスクリプションを追加し、AWS Lambdaや外部サービスと連携してSlackにメッセージを送信（一般的にはSNS→Lambda→Slack Webhook）

このような構成で、CloudWatchの監視結果をメールやSlackでリアルタイムに通知することが可能です。

WebアプリケーションのAPIは主に以下のような種類に分類されます。

RESTful API （レストフル エーピーアイ）

HTTPプロトコルをベースに、URLでリソースを表現し、GET ゲット/POST ポスト/PUT プット/DELETE デリートなどのメソッドを使用します。

構造がシンプルで理解しやすく、広く利用されています。

GraphQL API （グラフキューエル エーピーアイ）

クライアントが必要なデータ構造を指定し、サーバーがそれに応じたデータを返します。複雑なデータ取得やフロントエンドの柔軟な要件に適しています。

WebSocket API （ウェブソケット エーピーアイ）

双方向のリアルタイム通信をサポートし、チャットやリアルタイム通知などの用途に適しています。

OpenAPI／Swagger （オープンエーピーアイ／スワッガー）

APIの種類ではなく、API仕様やドキュメント標準です。RESTful APIの定義や自動ドキュメント生成によく使われます。

まとめると、WebアプリケーションではRESTful APIやGraphQL APIが最も一般的であり、用途に応じて他のAPIも選択されます。
